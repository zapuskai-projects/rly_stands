# Правила работы с репозиторием набора стендов

Репозиторий — набор учебных стендов на компьютере студента: консольный пульт, compose с модулями, образ «Linux-сервер для тестировщика». Всё, что здесь лежит, открыто: прячем только токен и данные студента.

## Код

1. Комментарии в коде не пишем — ни в TypeScript, ни в Python, ни в shell, ни в yaml. Исключение — одна строка «почему» на неочевидном решении, которое иначе «починят» обратно. Ссылки на задачи, этапы и даты в коде запрещены.
2. Файл — не больше 400 строк. Больше — режем по зонам ответственности.
3. Пульт (`pult/`): Node 22 и TypeScript, вывод в терминал только через `util/out.ts` (`console.*` запрещён линтером), чистая логика отдельно от Docker и сети и покрыта тестами `node:test`.
4. Решения вроде «хватает ли памяти», «что остановить агенту», «что показать в меню» — чистые функции с тестами. Работа с Docker и платформой — тонкие обёртки.
5. Новая зависимость нужна коду, который лежит в том же изменении. Пакет без использования удаляется.

## Проверки задач

1. Список проверок и действий задачи ведёт платформа (реестр в бэкенде, отдаёт `GET /api/stand-kit/primitives`). Пульт реализует тот же список в `pult/src/probes/`: один файл на модуль, таблица `ключ -> исполнитель`, сборка в `registry.ts`. `./stand doctor` сверяет оба списка.
2. Новая проверка — запись в реестре платформы и исполнитель в пульте с тем же ключом. Больше нигде ничего не правится.
3. Исполнитель возвращает факты в форме, которую описывает `sample` записи реестра. Если не ответил сам модуль — бросает `ProbeError`: платформа покажет «проверка не состоялась». Если студент не создал нужное или ошибся в своём файле — это не сбой, а факты (`exists: false`, `parsed: false`, `queryError`).
4. Разбор файлов студента, примеры против схем и рендер вывода — чистые функции с тестами на образцах; сеть и Docker — тонкие обёртки поверх них.
5. Исполнители с сетью проверяются на живых модулях: `cd pult && npm run test:live [группа]` (группы `messaging`, `data`, `contracts`, `camunda`, `bank`, `monitoring`; без аргумента — все). Скрипт поднимает нужные сервисы набора, гоняет `src/**/*.live.ts` в образе пульта с `buf`, `oasdiff` и `xmllint` и убирает за собой; при уже существующих контейнерах или томах `stands-kit*` он отказывается стартовать. Обычные тесты (`npm test`) живых модулей не требуют.

## compose.yaml

1. Порты открываются только на `127.0.0.1`.
2. Тома — только именованные (`name: stands-kit-…`, метка `stands.kit.module` с профилем модуля) или абсолютные пути вида `${KIT_HOST_DIR}/…`. Относительные пути запрещены: compose запускается из контейнера пульта, и относительный путь разрешится не на той машине.
3. Образы закреплены точной версией, `latest` и плавающих тегов нет. Образы пульта и linux-сервера берут версию из `VERSION` через `KIT_VERSION`.
4. Каждый модуль — один профиль, у каждого сервиса метка `stands.kit.module=<профиль>`. У профиля есть проверка готовности в `pult/src/modules/readiness.ts`.
5. Конфигурация модулей задаётся при сборке compose (`configs:` со встроенным содержимым), без файлов на компьютере студента.
6. Учётки модулей фиксированные и учебные; они перечислены в `README.md`.
7. Всё это проверяет `pult/src/compose-rules.test.ts`.

## Выпуск

1. В `main` лежит только выпущенное, разработка идёт в `develop`.
2. Версия набора — файл `VERSION`. Выпуск — тег `vX.Y.Z`, который совпадает с `VERSION`; образы `stands-kit-pult` и `stands-kit-linux` собирает и публикует только GitHub Actions (`release.yml`) под `linux/amd64` и `linux/arm64`. Руками образы не публикуем.
3. Поднимая версию, меняем `VERSION` и `version` в `pult/package.json` одним коммитом.
4. Минимальную версию пульта и версию для студентов выставляет суперадмин платформы; студент, у которого версия ниже минимальной, не сможет запускать стенды, пока не сделает `git pull`.
