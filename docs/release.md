# Выпуск набора

Обычный выпуск начинается с push в `main`. Временные ветки можно использовать для разработки, но отдельная ветка выпуска, ручное изменение версии и ручной тег не требуются.

GitHub Actions сначала выполняет все задания `ci`: пульт, браузерную панель с живыми контейнерами, compose, сборки образов и банк. Только после их успешного завершения вызывается `release.yml`.

Выпуск выбирает следующую версию относительно существующих тегов. Если в исходниках уже подготовлена более высокая версия, используется она; иначе увеличивается patch. `VERSION`, `pult/package.json` и корневые версии `pult/package-lock.json` меняются одним коммитом. Публикуются образы пульта, Linux-сервера и банка для `linux/arm64`.

После успешной сборки всех трёх образов Actions атомарно отправляет коммит версии в `main` и соответствующий тег, затем создаёт GitHub Release с признаком `stands-kit-images-ready`. Платформа читает только завершённые стабильные релизы с этим признаком. Релизный коммит не запускает ещё один выпуск: push выполняется стандартным `GITHUB_TOKEN`.

Backend платформы проверяет выпуск не чаще раза в пять минут. Полученная версия становится доступна через обычную сессию набора, поэтому существующий пульт предлагает обновление без ручной правки «Версии для студентов». Сохранённая настройка остаётся нижней границей объявляемой версии, минимальная версия не изменяется. При недоступном GitHub сохраняются последняя известная версия и существующие настройки.

Студент видит предложение в открытой панели либо при запуске `./stand` и подтверждает установку. Выключенный пульт покажет предложение при следующем запуске. Данные и `work/` сохраняются; при установке банк может кратко перезапуститься. Обновление Docker само по себе новую версию набора не устанавливает.

## Если выпуск не завершился

- Упал CI или сборка образа: исправить причину и отправить обычный push в `main`; готовый выпуск не объявляется до успешного завершения.
- Новая правка уже попала в `main`, пока предыдущая проверялась: старый выпуск пропускается. Если `main` изменился во время публикации образов, отправка релизного коммита отклоняется без перезаписи ветки и без объявления обновления. Следующий успешный CI выпустит актуальный код.
- Коммит версии и тег отправлены, но создание GitHub Release не удалось: повторить неудавшееся задание в исходном CI. Подготовленный релизный коммит распознаётся, номер не повышается повторно. Уже опубликованные образы в этом случае только проверяются, а не перезаписываются.
- Branch protection запрещает Actions отправлять коммит в `main`: выпуск завершится ошибкой до объявления обновления. Штатному Actions нужен разрешённый способ отправить релизный коммит; отключать защиту ветки из скрипта нельзя.

После коммита Actions локальную ветку разработчика нужно обновить обычным `git pull --ff-only` перед следующей отправкой.
